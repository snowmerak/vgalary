# 로그 추가 계획

상태: 구현·격리 검증 완료. 갱신일: 2026-10-31 (Asia/Seoul). 대상: vgalary 백엔드 구현자와 로컬 서버 운영자. 사용자 운영 서버에는 적용하지 않았다.

이 문서는 추가한 진단 로그의 범위·구현 결정·검증 결과를 관리한다. 현재 API 동작은 [API 문서](api.md), 전체 설계는 [blueprint](blueprint.md)를 따른다. 이벤트나 출력 정책을 바꾸면 이 문서와 관련 검증을 함께 갱신한다. 사용자 미디어·운영 데이터와 에이전트 스킬은 변경하지 않았다.

## 1. 목적과 범위

로그로 다음 질문에 답할 수 있게 한다.

| 운영 질문 | 남길 정보 |
| --- | --- |
| 색인이 시작됐는가, 지금 어디에서 시간을 쓰는가? | 작업 시작, 현재 단계, 단계 경과 시간, 마지막 처리 진전 이후 시간 |
| 종료·취소·중단 중 무엇이 발생했는가? | 작업 결과와 이유, 처리 개수, 이번 실행의 소요 시간, 상태 저장 성공 여부 |
| 임베딩·Qdrant·FFmpeg 중 어디에서 실패했는가? | 의존 서비스·작업 종류, 오류 코드, HTTP 상태 또는 자식 프로세스 종료 코드 |
| 자동 재시도가 진행 중인가? | 시도 번호, 대기 시간, 재시도 이유, 최종 결과 |
| 재시작 후 무엇이 재개됐는가? | 이전 작업 ID와 새 실행 ID, 재개 사유 |
| 색인은 끝났는데 검색에는 왜 반영되지 않았는가? | 프로필 준비·활성화·다른 소스 대기 구분 |
| 벡터 정리 실패가 남아 있는가? | 정리 작업 ID, 실패·재시도·복구, 남은 정리 작업 수 |

기본 `info`에서는 작업 흐름·주기적 요약과 의미 있는 실패를 기록한다. 파일별 정상 처리와 개별 외부 호출의 성공은 `debug`로 제한한다. 프레임마다 로그를 출력하지 않는다.

SQLite의 작업·색인·정리 의도가 계속 기준 상태다. 로그는 진단용이며, 복구·재시도·성공 판정에서 로그를 읽지 않는다. 기존 DB 상태와 UI로 충분한 정보는 로그에 전체 객체로 복제하지 않는다.

초기 범위에는 로그 DB, 로그 조회 UI, 파일 회전, 원격 수집기, OpenTelemetry, 메트릭 서버, 영구 이벤트 이력이나 이벤트 소싱을 추가하지 않는다. 필요성이 확인되면 별도 계획으로 다룬다.

## 2. 구현 전 기준 상태

다음은 구현 착수 전에 확인한 누락이며, 현재 구현 완료 여부는 10절에서 구분한다.

- `cmd/vgalary/main.go`: 표준 `log/slog`로 서버 시작과 일부 기동·종료 오류를 출력한다. 시작 메시지는 현재 소켓 바인딩 전에 출력하므로 실제 준비 완료를 보장하지 않는다.
- `internal/backend/app.go`: 작업 상태와 오류를 SQLite에 저장한다. 작업 시작·재개·종료 로그는 없다. worker의 작업 조회 실패는 다음 순회로 넘어가며, 작업 종료 상태 저장 오류도 로그로 드러나지 않는다.
- `internal/backend/clients.go`: 외부 요청을 최대 3회 시도한다. 상태 코드·네트워크 실패를 반환하지만 요청별 소요 시간과 재시도 과정은 출력하지 않는다. 네트워크 오류는 현재 일반 메시지로 축약된다.
- `internal/backend/media.go`: 실행별 시간 제한과 출력 크기 제한이 있다. 수집한 FFmpeg/ffprobe stderr를 로그로 출력하지 않으며, 일반 실패 메시지만 반환한다.
- `internal/backend/scan.go`, `index.go`: 파일별 오류를 `JobIssue`로 모으고 작업 결과에 반영한다. 보존된 오류 목록은 최대 100개이며, 영상·임베딩·저장 단계의 진단 로그는 없다.
- 전체 색인 작업의 타임아웃은 제거된 상태다. 이 계획은 전체 시간 제한을 다시 도입하지 않는다.

## 3. 출력과 구성

기존 `log/slog`를 재사용한다. 로깅 라이브러리나 외부 서비스 의존성을 새로 추가하지 않는다.

다음 실행 옵션을 구현했다. 사용법은 [배포 문서](deployment.md#진단-로그)를 따른다.

| 실행 옵션 | 기본값 | 의미 |
| --- | --- | --- |
| `-log-level` | `info` | `debug`, `info`, `warn`, `error` 중 최소 출력 레벨 |
| `-log-format` | `json` | 한 줄당 JSON 한 개. 터미널용 `text`도 지원 |
| `-log-paths` | `false` | 명시적으로 켰을 때만 소스 상대 경로와 중첩 압축 항목 이름 포함 |

출력 대상은 stderr 한 곳이다. 파일 보관·회전·전달은 실행 셸이나 서비스 관리자가 맡는다. 앱이 자동으로 로그 파일을 만들어 무한히 누적하지 않는다. 보존 기간과 공유 범위도 운영자가 결정한다.

로거는 CLI 조립 지점에서 생성하여 앱과 하위 실행 경로에 전달한다. 기존 `New(ctx, dir)` 호출은 유지할 수 있는 생성 옵션 형태로 확장하고, 테스트에서는 독립된 로거와 수집기를 주입한다. 전역 기본 로거를 테스트마다 교체하지 않는다. 작업 실행 전에 로거가 구성되어야 한다.

로그 레벨·형식·경로 노출은 프로세스 실행 옵션으로만 관리한다. 이번 범위에 SQLite 설정·환경 변수 우선순위·설정 UI를 추가하지 않는다. 옵션 변경은 재시작 후 적용되며 색인 프로필이나 재임베딩 여부에 영향을 주지 않는다.

## 4. 필드와 식별

| 필드 | 규칙 |
| --- | --- |
| `time`, `level`, `msg` | UTC 시각, 로그 레벨, 짧은 영어 메시지. 작업 경로의 메시지는 이벤트 이름이며 UI 언어와 독립적 |
| `event` | `job.started` 같은 고정 이름. 분석은 문장 대신 이 필드 사용 |
| `listen_address` | 바인딩에 성공한 로컬 loopback 주소. `server.started`에서 실제 선택된 포트 확인 |
| `instance_id` | 프로세스 시작마다 생성. 재시작 경계 구분 |
| `job_id`, `source_id`, `profile_id` | 해당 실행에서 알고 있는 기존 ID만 기록 |
| `run_id` | 작업 실행·재개마다 생성. 같은 `job_id`의 서로 다른 실행 구분 |
| `request_id`, `operation_id` | HTTP 요청과 논리적인 외부 호출 식별. 외부 호출 재시도에는 동일 `operation_id` 사용 |
| `asset_id` / `item_id` | 미디어 ID가 있으면 사용. 생성 전 탐색 항목에는 실행 범위의 임시 `item_id` 사용 |
| `stage`, `operation`, `dependency` | 고정된 단계·동작·의존성 이름. 예: `hash`, `embedding.image`, `qdrant`, `ffmpeg` |
| `duration_ms`, `stage_elapsed_ms`, `last_progress_age_ms`, `retry_delay_ms` | 단위를 이름에 명시. 경과 시간은 단조 시간 기준으로 계산 |
| `result`, `reason`, `error_code` | 상태·결과와 안전한 분류 코드. 임의 오류 문자열을 코드로 사용하지 않음 |
| `attempt`, `attempts`, `http_status`, `exit_code` | 실제 관찰한 경우만 기록. 재시도 번호는 1부터 시작 |
| `discovered`, `indexed`, `reused`, `embedding_calls`, `cycles`, `issue_count` | 이름별 의미를 기존 작업 카운터와 맞춤. 전체 대상 개수를 모르면 진행률을 만들지 않음 |

대기 상태에서 취소된 작업에는 `run_id`가 없을 수 있다. 취소 HTTP 요청의 `request_id`와 취소되는 작업의 `job_id`를 함께 기록하되, 요청이 끝나도 작업 실행 문맥은 유지한다. 검색·연결 확인처럼 작업이 없는 경로에는 `job_id`를 억지로 만들지 않는다.

HTTP 요청 ID는 서버에서 생성하며 외부 헤더를 그대로 식별자나 로그 필드로 사용하지 않는다. `attempt`는 현재까지 실행한 시도 번호이며 재시도 이벤트에서는 실패한 시도를 가리킨다. 최종 요약의 `attempts`는 총 시도 횟수다.

사용자 취소, 소스 제거, 서버 종료를 구분하는 내부 사유를 전달한다. `context.Canceled`만 보고 원인을 추정하지 않는다. 요청 제한과 FFmpeg 실행 제한도 각각 `request_timeout`, `process_timeout`으로 분류하며 기존 취소·반환 오류 의미는 보존한다.

## 5. 이벤트와 기록 위치

| 이벤트 | 레벨 | 기록 책임과 조건 |
| --- | --- | --- |
| `server.started` / `server.stopping` / `server.stopped` | info | CLI. 소켓 바인딩 성공 후 시작 기록, 종료 요청과 실제 정리 완료 구분 |
| `server.failed` | error | CLI가 소유한 기동·서버·종료 실패 |
| `job.queued` / `job.started` / `job.resumed` | info | `app.go`. 해당 상태 저장 성공 후 기록 |
| `job.progress` | info | 실행 중인 작업마다 최대 30초에 한 번 현재 단계와 카운터 요약 |
| `job.cancel_requested` | info | 취소 요청을 수락한 경계. 취소 완료는 `job.finished`에서 확인 |
| `job.finished` | info / error | `runJob`. 완료·예상 취소는 info, 작업 실패는 error. 결과 상태 저장 성공 후 한 번 기록 |
| `job.interrupted` | info | 서버 종료로 재개 가능한 상태를 남긴 실행. 완료·사용자 취소로 오인하지 않음 |
| `job.persist_failed` / `worker.poll_failed` | error | 상태 저장·작업 조회를 책임지는 지점. 정상 종료로 기록하지 않음 |
| `file.failed` | warn | 탐색·파일 처리 오류를 작업 이슈로 확정하는 지점. 세부 단계와 오류 코드 포함 |
| `file.processed` | debug | 파일 처리 종료 시 한 번. 색인·재사용 결과와 소요 시간 |
| `media.frames_selected` | debug | 영상당 후보·선택 프레임 수와 정책 요약. 개별 프레임 로그 없음 |
| `dependency.retry` | warn | `clients.go`. 실제 재시도 대기 직전, 원인·시도·대기 시간 기록 |
| `dependency.finished` / `media.finished` | debug | 논리적인 외부 호출·프로세스의 최종 결과와 소요 시간. 이미지 임베딩에는 실제 입력 수 `batch_size`를 포함. 작업 카운터의 `embedding_calls`는 배치 요청 횟수, `embedded_images`는 정상 응답 이미지 수. 최종 실패의 warn/error 책임은 상위 작업·파일·요청 경계에 둠 |
| `profile.ready` / `profile.waiting` / `profile.activated` | info | `index.go`. 소스 준비와 검색 프로필 활성화, 다른 소스 대기 구분 |
| `cleanup.failed` / `cleanup.recovered` | warn / info | `app.go`. 영속 정리 작업의 실패와 이후 복구. 반복 실패는 집계 |
| `http.failed` | error | HTTP 처리 경계의 5xx. API 실패를 최종적으로 소유한 곳에서 기록 |
| `http.finished` | debug | HTTP 메서드·라우트 템플릿·상태·소요 시간. 정상 2xx·예상 4xx와 폴링은 기본 레벨에서 출력하지 않음 |

`job.progress`는 작업이 살아 있다는 관찰이다. 카운터가 늘지 않았다는 이유만으로 멈춤·실패라고 판정하지 않는다. 현재 단계, 그 단계에서 머문 시간, 마지막 처리 진전 이후 시간을 함께 보여 오래 걸리는 단일 파일도 확인할 수 있게 한다. 메모리의 작은 진행 스냅샷을 읽으며 로그를 위해 DB를 주기적으로 추가 조회하지 않는다.

파일·의존성 실패의 상세 내용은 소유 경계에서 한 번 기록한다. 이후 `job.finished`는 전체 실패 개수와 대표 오류 코드만 요약한다. HTTP로 시작한 작업이 나중에 실패해도 이미 성공한 작업 등록 요청을 `http.failed`로 기록하지 않는다. Qdrant 벡터 재사용 확인 중의 예상 404와 사용자 취소를 의존성 장애로 기록하지 않는다.

상태 저장이 실패하면 `job.persist_failed`에 의도한 결과를 기록하고 성공한 `job.finished`를 만들지 않는다. 로그 기록 성공 여부는 DB 저장 성공의 증거가 아니다. 재개된 실행의 시간과 카운터는 이번 `run_id` 기준임을 명확히 한다.

## 6. 민감 정보와 출력량

- API Key·비밀번호·토큰·쿠키·Authorization 헤더·환경 변수 값·검색어·요청/응답 본문·이미지 base64·벡터·모델 프리셋을 출력하지 않는다. `debug`에서도 동일하다.
- 원본·데이터 디렉토리의 절대 경로, 전체 URL과 쿼리 문자열, 자식 프로세스 인자와 stderr 원문은 출력하지 않는다. `-log-paths`를 켜도 허용 범위는 소스 상대 경로와 압축 항목 이름이다.
- `err.Error()`를 그대로 구조화 필드에 넣지 않는다. 네트워크 오류·파일 오류·자식 프로세스 오류를 안전한 분류와 허용 필드로 변환한다. HTTP 응답·기존 `JobIssue`의 표시 계약을 로그를 위해 바꾸지 않는다.
- 상한은 레코드당 4 KiB, 선택 문자열은 최대 512바이트다. UTF-8 경계에서 자르고 `truncated=true`로 표시한다. 필드가 많아 전체 상한을 넘으면 이벤트·상관 ID 중심으로 필드를 줄이고 남은 문자열도 더 짧게 제한한다. 금지 필드 제외는 자르기 전에 수행한다.
- 같은 작업·단계·오류 코드의 파일 오류와 반복 의존성 재시도는 처음 5건만 상세 기록하고, 이후에는 30초 요약과 종료 요약에 `suppressed_count`를 기록한다. 중복 억제 키는 실행당 최대 64개로 제한하고 초과분은 기타 요약에 합친다. 서로 다른 오류의 무제한 맵을 만들지 않는다.
- 반복되는 worker·정리 오류도 첫 실패를 남기고 30초 단위로 집계한다. 복구 시 억제된 횟수와 복구 결과를 기록한다. 억제는 진단 출력에만 적용하며 DB 오류 개수·재시도 정책은 변경하지 않는다.

느리거나 닫힌 출력 대상이 색인·API를 멈추게 하지 않도록, 로그 출력 앞에 상한이 있는 비동기 큐를 둔다. 큐는 256개 × 최대 4 KiB이며 writer가 처리 중인 레코드 하나는 별도다. 모든 레벨의 제출은 큐 공간을 기다리지 않는다. 큐가 찬 경우 레벨별 유실 개수를 집계하고 출력이 복구되면 `logging.dropped` 요약을 남긴다. 억제와 큐 유실은 다른 카운터다. 출력 실패를 같은 로거로 재귀 기록하지 않는다.

종료 시 기존 서버 종료 예산 안에서 최대 1초 동안 큐를 비운다. 출력 writer가 계속 막히면 대기를 끝내고 프로세스 종료를 진행한다. 강제 종료·프로세스 크래시·출력 장애에서 마지막 로그의 보존은 보장하지 않는다. 이 로그는 감사 기록이나 영속 작업 이력이 아니다.

## 8. 구현 순서와 완료 조건

### A. 로거와 안전한 출력 경계

1. CLI 출력 설정, 로거 주입, 공통 필드와 출력 큐를 추가한다.
2. 기존 기동 로그를 통합하고 소켓 바인딩 성공과 준비 완료 기록의 순서를 수정한다.
3. 허용 필드에 기반한 오류 분류, 크기 제한, 반복 억제와 큐 유실 집계를 구현한다.

완료 조건: 각 줄을 JSON으로 읽고 레벨로 제어할 수 있다. 출력 writer의 정지·실패에도 API·색인·종료가 계속 진행된다. 비밀 값으로 표시한 테스트 문자열이 출력에 섞이지 않는지 검사한다.

### B. 색인 작업의 실행 경로

1. 작업 등록·재개·시작·취소·진행·종료와 상태 저장 실패를 연결한다.
2. 탐색·파일 처리·프레임 선택·의존성 재시도·프로필 활성화·정리 결과를 연결한다.
3. 반환 오류의 원인 정보를 보존하여 로그의 단계·오류 코드·재시도 횟수를 채운다. HTTP 상태 코드와 기존 작업 취소·복구 동작은 유지한다.

완료 조건: 같은 `job_id`/`run_id`로 시작부터 최종 결과까지 찾을 수 있고, 종료 저장 실패·서버 중단·개별 요청 시간 초과를 구별할 수 있다. 기본 레벨에서 정상 파일·프레임 수에 비례하는 로그가 쌓이지 않는다.

### C. HTTP·문서와 실제 출력 검증

1. HTTP 실패·요청 상관 ID를 연결한다. `GET /api/jobs` 등 정상 폴링은 `debug`로 제한한다.
2. [배포 문서](deployment.md)에 stderr 수집과 제안 옵션의 실제 사용법을, [README](../README.md)에 짧은 안내를 추가한다. 동작이 구현된 뒤에만 실행 가능한 옵션으로 문서화한다.
3. 격리 앱에서 아래 시나리오를 실행하고 대표 JSON 출력과 실행한 검사·미실행 범위를 검증 기록에 남긴다.

검사는 임시 데이터 디렉토리, OS가 배정한 별도 포트, 가짜 임베딩·Qdrant와 독립된 로그 수집기로 실행한다. 현재 사용 중인 앱·SQLite·실제 모델·Qdrant는 조회하거나 변경하지 않는다. 단위 테스트에서는 시각·ID의 정확한 값과 문장 대신 이벤트·필드·레벨·상관관계·노출 금지 값을 검사한다. 타이머와 writer를 제어하여 실제 30초 대기 없이 주기·억제·종료를 검증한다.

코드 구현 시 Go 테스트·vet·빌드·모듈 정리와 사용 가능한 정적 검사를 수행한다. race 검사나 취약점 검사 도구가 실행 불가능하면 그 사실을 기록한다. 문서 작성 단계에서는 코드 검사 통과나 로그 구현 완료로 기록하지 않는다.

2026-10-31 검증 결과:

- 정상 색인·재사용의 작업 결과와 DB 카운터 일치, 동일 실행 ID 유지, 기본 레벨에서 정상 파일·호출 로그 제외를 확인했다. HTTP 래퍼를 추가한 뒤 Range 응답도 206·요청한 바이트 수를 유지했다.

- 가짜 서비스의 503→성공에서 동일 호출 ID·시도 번호·대기 시간, 개별 요청 시간 초과와 자식 프로세스의 시간 초과·종료 코드, 프로필 전환 대기·활성화, 불완전 압축 스캔, worker 조회 실패, 정리 실패·복구를 확인했다.
- 비밀 값·검색어·서버 응답·헤더·stderr 원문과 기본 경로 미노출, 선택 경로 상한, JSON/text의 UTF-8·한 줄 출력·4 KiB 상한을 검사했다.
- 막힌 writer 동안 1,001개 레코드를 제출하여 출력·드롭 합계가 제출 수와 일치하는지 검사했다. writer 실패 후 복구 집계와 종료 대기 상한을 확인했고, 가상 시간으로 30초 진행 주기와 reporter 종료를 검증했다.
- 실제 HTTP listener를 `127.0.0.1:0`에 바인딩해 health 200과 시작→종료 요청→종료 완료를 확인했다. 이미 사용 중인 테스트 포트에 바인딩을 실패시켰을 때 `server.started`가 출력되지 않았다.
- `VGALARY_LIVE_TEST`를 비운 `go test ./...`, `go vet ./...`, `go mod tidy`, `go build ./...` 통과. golangci-lint 2.15.0 기본 규칙(errcheck·govet·ineffassign·staticcheck·unused) 0 issues. `go.mod`·`go.sum`의 변경 없음.
- `go test -race`는 현재 Windows ARM64에서 지원되지 않아 실행 불가. 이후 `govulncheck v1.9.0`을 설치하고 `govulncheck ./...`에서 알려진 취약점이 발견되지 않았음을 확인했다(Go 1.27.3, windows/arm64, 취약점 DB 갱신 2026-10-27 21:16:18 UTC). 실제 llama.cpp·Qdrant와 사용자 운영 서버의 실행 검증은 수행하지 않았다.

`TestJobLogsMatchDurableResultAndDoNotExposeMedia`가 수집한 실제 `job.finished`에서 일부 필드만 발췌했다. 합성 예시의 성능 수치로 사용하지 않는다.

```json

```

현재 상한은 위 격리 시나리오에서 검증한 초기 운영값이다. 대규모 미디어 라이브러리에서의 로그 비용·처리량은 측정하지 않았다. 출력이 막힌 동안 `Close`는 기다리기를 끝내지만, 범용 writer의 막힌 OS 쓰기 자체를 강제로 중단하지는 못한다. writer 복구나 프로세스 종료 전까지 해당 출력 goroutine이 남을 수 있다. 짧은 쓰기·출력 장치 장애에서는 부분 레코드가 남을 수 있고, 강제 종료 시 마지막 로그가 유실될 수 있다.
